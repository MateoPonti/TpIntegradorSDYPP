4. El flujo en palabras

  1. Entrada. POST /transactions o /transactions/bulk. El coordinador valida el formato, el saldo y la firma (si la usamos) y la agrega a tx:pending. Responde 202: la transacción todavía no está en la cadena.
  2. Plan del pool. Cada 15 s el pool líder lee cuántos mineros GPU y CPU están vivos (worker:*) y el largo de mining.tasks. Con eso publica pool:plan (prefijo efectivo y fragmentación) y pool:scaling (la señal para KEDA).
  3. Armado. Cuando hay MAX_TX_PER_BLOCK transacciones o pasaron BLOCK_TIMEOUT segundos desde la primera pendiente (o enseguida después de sellar un bloque, si hay pendientes), el coordinador líder arma el candidato: base = previous_hash + tx_digest, donde tx_digest es el SHA-256 de las transacciones en JSON canónico. El prefijo del plan se guarda en el bloque.
  4. Publicación (NCT.1). El coordinador parte el espacio de nonces según la fragmentación del plan y publica una tarea task.* por rango, por tandas: cuando en la cola quedan menos tareas que mineros vivos, publica la tanda siguiente desde block:<i>:next_from. El pool decide los parámetros y el coordinador es el único que publica.
  5. Préstamo. El minero hace keep-alive y pide trabajo con GET /tasks/next. El gateway hace basic_get y ack, y registra el préstamo en lease:<task> con TTL.
  6. Minado (NCT.2). El wrapper corre miner_gpu por tramos dentro del rango. Entre tramo y tramo consulta si la tarea sigue vigente. El binario CUDA no se entera a mitad de una ejecución.
  7. Resultado. POST /results con encontrado o no encontrado. El gateway publica result.* y borra el lease.
  8. Verificación (NCT.3). Un coordinador consume el resultado y recalcula el MD5. Descarta resultados inválidos, de bloques viejos o duplicados.
  9. Cierre (NCT.4). Un script Lua en Redis guarda el bloque solo si chain:tip sigue siendo el previous_hash. Si dos coordinadores llegan a la vez, gana uno solo. Después el coordinador publica block.solved y hace ack.
  10. Aviso. Cada gateway recibe block.solved por su cola exclusiva y marca el bloque como cerrado. La próxima consulta de cada minero devuelve 410 y el minero abandona.
  11. Falla. Si un minero muere, su lease vence y el reaper del gateway re-publica el rango. Después de 3 intentos, la tarea va a mining.dlq, donde nadie la reprocesa: queda como alarma y evidencia. El bloque no se traba porque se siguen publicando rangos nuevos.
  12. Observabilidad. Prometheus scrapea /metrics de los servicios y de los exporters. GET /status del coordinador consulta a RabbitMQ, Redis, el gateway y el pool, y devuelve un JSON con el estado de cada servicio.
